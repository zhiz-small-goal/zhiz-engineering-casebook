# 工程问题案例库（Engineering Casebook）

这里收集技术实践中遇到的错误、异常和难题，也记录查明问题时走过的弯路，以及真正有用的解决办法。

目标很简单：**下次遇到类似问题能快速查到，以后想写教程时也有可靠素材。** 它是工程问题的案例库，不是完整日志备份，也不是提前建设好的内容生产系统。

## 目录设计

```text
cases/
  infrastructure/        # 操作系统、网络、容器、部署、服务依赖
    networking/           # 网络、端口、代理、DNS、TLS 等
  development/            # 开发工具、依赖、构建、调试
  applications/           # 应用本身的接口、业务逻辑或集成
  data/                   # 采集、清洗、结构化、存储和评测
  ai/                     # 模型、推理、检索、Agent 与模型服务
templates/
  case.md                 # 新案例模板
```

上述尚无案例的目录只是**未来可用分类**，不会为了凑结构创建空目录。

**归档规则：** 首先选择问题实际发生的工程层级（例如网络端口冲突归 `infrastructure/networking`），不是仅按当时使用的软件分类。软件、组件和症状放在 Markdown 元数据中。真正归因不明时，先记录 `investigating`，之后根据证据移动分类，保留 Git 历史。

## 每条案例需要回答什么

1. **环境和现象**：在什么条件下出现了什么问题？
2. **关键证据**：足以支撑判断的命令、少量日志、状态码和来源。
3. **排查实验**：每一步想区分什么假设，观测是什么？
4. **原因与可信度**：哪些已证实、哪些仍是推断？
5. **处理和验证**：是找到绕过办法、修复根因，还是尚未解决？
6. **迁移经验**：下次碰到类似症状，先检查什么？

状态约定：`investigating`（排查中）、`workaround_verified`（绕过方案已验证）、`resolved_verified`（根因修复已验证）、`closed_unconfirmed`（结束但未确认根因）。

**不把绕过成功写成根因已修复，不把合理猜测写成确定事实。**

## 记录与写作原则

1. **先解决问题，再顺手记录。** 归档是为了省下次的时间，不是再给自己增加一个维护项目。只收值得复用的案例，不追求每次操作都入库。
2. **说人话，口语化。** 尽量像向另一个开发者讲自己的经历：是什么现象、怎么发现的、做了哪些测试、最后怎么处理。少用空洞的套话和生硬的公文腔。专业名词、原样命令和错误信息需要时照常保留，首次出现的关键概念可用一句话解释；口语化不等于含糊。
3. **事实、推断和未知分开。** 亲手测到什么就写什么；原因如果只是一种推测，就明确标注。绕过成功不等于根因已经修复；有新证据时再更新结论。
4. **只保留够用的关键证据。** 默认摘录能够解释诊断的日志片段、配置片段、命令和输出，**不要求完整保存原始日志、整份配置或另建私有证据库**。但也不要只留一句“已经解决”：读者应能看懂判断从何而来。极少数无法重现、又特别重要的证据，可视情况另行保留。
5. **按问题本身分类，持续小步更新。** 一个问题一篇 Markdown，有固定 ID；目录按工程领域分类，软件名放在文件名/标签中；不预建空目录，也不为同一问题反复创建 `v2`、`final` 等副本。
6. **先保留真实过程，再考虑写教程。** 公开案例忠实记录排查，包括失败的假设与剩余疑点。未来确实想发布时，再改写成适合读者的文章；不为每篇案例强制设置选题、推广或发布流程。
7. **公开前做隐私检查。** 本仓库是 Public。不要提交密码、Token、Cookie、API Key、敏感地址、个人资料，或可能夹带这些信息的完整配置/日志。只把必要的上下文脱敏后写进文档；Git 历史不会因为后来删掉一段文字就自动消失。

### 口语化的例子

- 不推荐：“经系统化故障归因分析，最终定位为宿主机端口层面的异常行为。”
- 推荐：“容器里访问正常，Windows 上却一直报错。继续查才发现，80 端口还有一条 `portproxy` 转发规则。”

**判断是否写得好：** 一段时间后自己看得懂，其他人能复查关键步骤，而且没有把猜测讲成事实。

## 维护方式

- 发现问题并排查后，直接在 `cases/` 对应领域新建案例，同步更新 [分类索引](cases/README.md)。
- 后续找到新证据或发现当时判断有误，就修改原文件，保留相关证据；Git 提交历史负责记录变化。
- 不要求额外建立截图目录、原始日志归档、私有仓库或教程生产流水线。确有需要再增加，不提前复杂化。
