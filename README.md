# 工程问题案例库（Engineering Casebook）

持续记录技术实践中遇到的错误、异常、排障过程、失败假设与有效经验。它不是只收集“做错的题”，而是保留**可复查的工程证据与推理过程**。

## 目录设计

```text
cases/
  infrastructure/        # 操作系统、网络、容器、部署、服务依赖
    networking/           # 网络、端口、代理、DNS、TLS 等
  development/            # 开发工具、依赖、构建、调试
  applications/           # 应用本身的接口、业务逻辑或集成
  data/                   # 采集、清洗、结构化、存储和评测
  ai/                     # 模型、推理、检索、Agent 与模型服务
templates/
  case.md                 # 新案例模板
```

上述尚无案例的目录只是**未来可用分类**，不会为了凑结构创建空目录。

**归档规则：** 首先选择问题实际发生的工程层级（例如网络端口冲突归 `infrastructure/networking`），不是仅按当时使用的软件分类。软件、组件和症状放在 Markdown 元数据中。真正归因不明时，先记录 `investigating`，之后根据证据移动分类，保留 Git 历史。

## 每条案例需要回答什么

1. **环境和现象**：在什么条件下出现了什么问题？
2. **原始证据**：关键命令、日志片段、状态码和来源。
3. **排查实验**：每一步想区分什么假设，观测是什么？
4. **原因与可信度**：哪些已证实、哪些仍是推断？
5. **处理和验证**：是找到绕过办法、修复根因，还是尚未解决？
6. **迁移经验**：下次碰到类似症状，先检查什么？

状态约定：`investigating`（排查中）、`workaround_verified`（绕过方案已验证）、`resolved_verified`（根因修复已验证）、`closed_unconfirmed`（结束但未确认根因）。

**不把绕过成功写成根因已修复，不把合理猜测写成确定事实。**

## 维护与安全

- 每个案例有稳定的 `id`；优先原位修改而不是创建 `final-v2` 等副本。
- 修改案例时保留被推翻的假设和证据；纠错不抹掉排查过程。
- 本仓库目前是 **Public**：只提交已脱敏片段，不提交 Token、Cookie、密码、个人路径、账户信息或整份可能含敏感信息的日志。
- 图片或大型日志应另存适当的位置，在案例中放链接与必要摘要，不把仓库当备份盘。
